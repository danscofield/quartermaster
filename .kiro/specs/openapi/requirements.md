# Requirements Document — OpenAPI Spec Generation via `utoipa`

## Introduction

This spec adds OpenAPI documentation generation to Quartermaster using `utoipa`. The OpenAPI spec is derived from code annotations on handlers and types, ensuring it never drifts from the implementation. The generated spec is served at runtime and used for auto-generating client libraries.

## Requirements

### Requirement 1: utoipa Integration

#### Acceptance Criteria

1. Add `utoipa` and `utoipa-axum` as dependencies
2. Annotate all public handler functions with `#[utoipa::path(...)]` including: method, path, request body schema, response schemas, tags, and description
3. Annotate all request/response structs with `#[derive(utoipa::ToSchema)]`
4. Define a top-level `#[derive(utoipa::OpenApi)]` struct aggregating all paths and schemas

### Requirement 2: Serve OpenAPI JSON at Runtime

#### Acceptance Criteria

1. THE server SHALL serve the generated OpenAPI JSON at `GET /openapi.json`
2. THE endpoint SHALL require no authentication (public, like OIDC discovery)
3. THE OpenAPI document SHALL include: info (title, version, description), all paths, all schemas, and security schemes
4. THE security schemes SHALL include:
   - `BearerAuth` — Bearer JWT in Authorization header (for admin endpoints and `/billets/{name}`)
   - `MutualTLS` — mTLS client certificate (for `/token` and `/billets/me` when subject_token is omitted)
5. THE `GET /openapi.json` endpoint itself SHALL NOT appear in the documented paths (it is meta-documentation)

### Requirement 3: All Endpoints Documented

#### Acceptance Criteria

1. THE following endpoints SHALL be annotated:
   - `POST /token` — token exchange (content-type: `application/x-www-form-urlencoded`)
   - `POST /billets/me` — billet discovery (content-type: `application/x-www-form-urlencoded`)
   - `GET /.well-known/openid-configuration` — OIDC discovery
   - `GET /jwks.json` — JWKS
   - `GET /ca/chain.pem` — CA trust bundle
   - `GET /billets/{name}` — billet metadata (data-plane)
   - `GET /healthz` — health check
   - `POST /admin/billets` — create billet
   - `GET /admin/billets` — list billets
   - `GET /admin/billets/{name}` — get billet
   - `PUT /admin/billets/{name}` — update billet
   - `DELETE /admin/billets/{name}` — delete billet
   - `POST /admin/billets/{name}/policies` — create policy
   - `GET /admin/billets/{name}/policies` — list policies
   - `GET /admin/billets/{name}/policies/{id}` — get policy
   - `PUT /admin/billets/{name}/policies/{id}` — update policy
   - `DELETE /admin/billets/{name}/policies/{id}` — delete policy
2. Each endpoint SHALL document all possible response codes and their schemas
3. Endpoints SHALL be grouped with the following tags:
   - `token-exchange` — `POST /token`
   - `discovery` — `POST /billets/me`, `GET /.well-known/openid-configuration`, `GET /jwks.json`, `GET /ca/chain.pem`, `GET /billets/{name}`
   - `admin-billets` — all `/admin/billets` CRUD endpoints
   - `admin-policies` — all `/admin/billets/{name}/policies` CRUD endpoints
   - `system` — `GET /healthz`
4. `POST /token` and `POST /billets/me` SHALL be documented with content-type `application/x-www-form-urlencoded` (not JSON) — utoipa annotations must specify `request_body(content_type = "application/x-www-form-urlencoded")`

### Requirement 4: Schema Annotations on Types

#### Acceptance Criteria

1. All request body types SHALL derive `ToSchema`: `TokenExchangeForm`, `BilletDiscoveryForm`, `CreateBilletRequest`, `UpdateBilletRequest`, `CreatePolicyRequest`, `UpdatePolicyRequest`
2. All response types SHALL derive `ToSchema`: `TokenExchangeResponse`, `BilletDiscoveryResponse`, `BilletMetadataResponse`, `BilletWithPoliciesResponse`, `PolicyResponse`, `ErrorResponse`, `HealthResponse`, `OidcDiscoveryDocument`
3. Enum variants and optional fields SHALL be correctly represented in the generated schema

### Requirement 5: Client Library Generation (Separate Repo)

#### Acceptance Criteria

1. THE OpenAPI spec served at `/openapi.json` SHALL be sufficient for codegen tools to generate working clients without manual intervention
2. THE spec SHALL use standard OpenAPI 3.1 features (no vendor extensions required for basic client generation)
3. THE repo SHALL include a `docs/openapi.yaml` file committed from CI (generated by hitting `/openapi.json` during build) for offline codegen use
